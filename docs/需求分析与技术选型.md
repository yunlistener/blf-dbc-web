# 需求分析与技术选型

## 1. 需求拆解

### 1.1 功能需求

**P0(第一版必须)**

1. **文件上传与管理**
   - 支持 .blf、.dbc 文件上传,GB 级 BLF 需分块/断点续传
   - 文件列表、删除、重命名
2. **DBC 解析展示**
   - 报文列表:ID(标准/扩展)、报文名、周期、长度
   - 信号详情:起始位、位长、字节序(Motorola/Intel)、缩放因子、偏移、单位、值表(如 `0=Off 1=On`)、最大值/最小值
3. **BLF 解析与统计**
   - 流式解析(不把整个文件读入内存)
   - 按仲裁 ID 统计:帧数、出现频率、时间范围
   - 区分 CAN / CAN FD / 远程帧 / 错误帧
4. **信号解码**
   - 输入:BLF + DBC → 输出:每条报文的每个信号的物理值序列
   - 支持按时间区间过滤、按信号筛选
5. **Web 后端与部署**
   - REST API + 浏览器页面
   - 树莓派 systemd 常驻服务,开机自启

**P1(第二版)**

6. **可视化**:信号时序折线图(时间轴缩放、框选放大、多信号叠加对比);ID 分布柱状图
7. **导出**:解码结果 CSV / JSON 下载

**P2(远期)**

8. 总线负载率估算、信号周期抖动分析、CAN FD 比特率切换统计
9. 多 BLF 文件对比、多 DBC 合并
10. 用户登录 / 权限(局域网多设备访问时)

### 1.2 非功能需求

| 约束 | 说明 |
|---|---|
| 硬件 | 树莓派 4/5,ARM64,内存 2–8 GB,SD 卡存储 |
| 数据规模 | BLF 常见 100 MB ~ 数 GB,解析必须流式、可后台化 |
| 并发 | 局域网内少量用户(1–5),无需高并发设计 |
| 易部署 | 一条脚本装好依赖 + systemd 注册即可运行,尽量少编译 |
| 隐私 | 数据不出局域网,无云依赖 |

## 2. 各部分语言 / 技术选型分析

### 2.1 BLF 解析引擎

| 方案 | 语言 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| `python-can`(BLFReader) | Python | 官方生态,读 BLF v1/v2/v3;与 `cantools` 天然配合 | 纯 Python 解析大文件偏慢(可接受,可后台任务化) | ✅ **首选** |
| `vblf` | Python | 纯 Python,读写都支持,专注 BLF | 生态较小 | 备选 |
| Vector `blf_lib` | C++ | 官方库,性能最好,能写 BLF | 需编译、写 C++ 绑定,开发成本高 | 引擎核心性能不足时再引入 |
| 自研 | 任意 | 完全可控 | BLF 是私有格式,逆向成本高、易踩坑 | ❌ 不推荐 |

**结论:Python + python-can。** 树莓派 ARM64 上有官方 wheel,免编译;解析速度足够(GB 级文件后台任务处理,前端轮询进度即可)。

### 2.2 DBC 解析引擎

| 方案 | 语言 | 说明 |
|---|---|---|
| `cantools` | Python | **事实标准**。解析 DBC、生成解码器、支持信号值表/多路复用,纯 Python |
| 自研解析器 | 任意 | DBC 格式简单(文本)但边界情况多(注释、值表、多路复用),没必要重复造轮子 |

**结论:Python + cantools,没有争议。**

### 2.3 Web 后端

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **FastAPI + Uvicorn** | 异步高性能;自动生成 Swagger 文档;类型校验;树莓派上内存占用小 | 相对 Flask 略重一点(可忽略) | ✅ **首选** |
| Flask | 极简、上手快 | 同步模型,大文件解析时会阻塞 | 备选 |
| Go (gin/echo) | 单二进制部署,内存效率高 | BLF/DBC 生态薄弱,解析库基本要自己写;开发周期长 | ❌ 不符合"快速落地 + 生态复用" |

**结论:FastAPI。** 树莓派部署 = `uvicorn` 一个进程,内存 < 100 MB;后台任务用 FastAPI 的 `BackgroundTasks` 或简单队列即可。

### 2.4 前端

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **原生 HTML/JS + ECharts** | 零构建、零依赖下载、资源占用最低;ECharts 时序图/柱状图开箱即用 | 复杂交互(多页签、状态管理)写起来繁琐 | ✅ **首选**(本场景页面不多) |
| Vue3 + Vite | 组件化,后续功能扩展舒服 | 需要 Node 构建链,部署多一层 | 界面复杂到一定程度再升级 |

**结论:原生 JS + ECharts。** 关键点:可视化全部在**浏览器端**完成,树莓派只托管静态文件 + 提供 API,负载极低。信号曲线按需加载(先出摘要,框选区间再拉取该区间原始数据),避免一次性传大 JSON。

### 2.5 部署与运维

| 组件 | 选型 | 理由 |
|---|---|---|
| 操作系统 | Raspberry Pi OS (Bookworm, ARM64) | 官方系统,Python 3.11 自带 |
| 进程管理 | systemd 服务 | 开机自启、崩溃重启、日志轮转,免 Docker 内存开销 |
| 反向代理 | Nginx(可选) | 静态文件 + API 同端口托管;不做也可由 Uvicorn 直接服务 |
| 依赖安装 | `pip install`(或 venv) | cantools / python-can / fastapi 在 ARM64 均有预编译 wheel,无编译步骤 |

## 3. 关键技术设计要点

1. **大文件流式解析**:BLFReader 逐帧迭代,统计阶段只保留聚合结果(每 ID 帧数/时间范围),不保留原始帧;解码阶段按需二次扫描 + 区间过滤。
2. **后台任务 + 进度轮询**:解析大文件是耗时操作,API 立即返回任务 ID,前端轮询进度百分比(或 WebSocket 推送)。
3. **信号数据分页加载**:时间序列数据量大,接口支持 `?start_time=&end_time=&max_points=` 降采样,前端 ECharts 大数据量模式(`large: true`)渲染。
4. **内存预算**:树莓派 4GB 内存下,解析峰值内存控制在 ~1GB 内(流式 + 聚合),避免 OOM。
5. **数据落盘**:上传文件存 `data/`,解析产物(统计 JSON、解码缓存)可选落盘,重启不丢。

## 4. 里程碑与验证

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| M1 | 后端:上传、DBC 解析 API、BLF 统计 API、解码 API | curl 跑通;用真实 BLF+DBC 输出统计与解码结果 |
| M2 | 前端:文件管理、报文/信号树、时序曲线、ID 统计图 | 浏览器完成"上传 → 看图 → 导出"全流程 |
| M3 | 树莓派部署 + 性能验证 | systemd 自启;1 GB BLF 解析 < 3 分钟;内存峰值 < 1 GB |
