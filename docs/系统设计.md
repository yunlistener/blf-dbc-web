# BLF/DBC CAN 总线分析平台 — 系统设计

> 版本:v1(2026-08-23)
> 依据:《需求文档》v84+(含新增"播放模式 + 动态解析推送"需求 §3)
> 原则:**抛开现有架构与代码**,按需求重新设计;核心目标 = 离线回放与实时接收共用同一套前后端管线

---

## 1. 设计目标与约束

| 目标 | 说明 |
|---|---|
| ① 对齐 CANoe 流程 | 配置网络 → 添加信号 → **播放** → 曲线动态显示 |
| ② 前后端一致接口 | 离线 BLF 回放与后期实时 CAN 接收,共用同一"帧批次推送 + 增量渲染"管线 |
| ③ 大数据量流畅 | 百万点级渲染(uPlot 保形降采样)、GB 级 BLF 流式处理 |
| ④ 易部署 | ARM64 免编译,单进程 systemd 常驻,局域网访问 |
| ⑤ 可扩展 | 数据源可插拔(离线/实时/未来更多),多用户(1-5 人) |

**约束**:数据不出局域网;内存峰值 ≤1GB;DBC 兼容 GBK/UTF-8;前端 Edge 缓存需版本号击穿。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────┐
│ 前端(浏览器)                                              │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐ │
│  │ 配置/文件 │ │ 信号树   │ │ 示波器区 │ │ Trace/统计   │ │
│  │ UI       │ │ + 已选列 │ │ (多窗口) │ │ /导出        │ │
│  └──────────┘ └──────────┘ └────┬─────┘ └──────────────┘ │
│  ┌──────────────────────────────▼──────────────────────┐ │
│  │ 播放控制台(状态机):▶ 播放 / ⏸ 暂停 / ⏹ 停止 / 进度条 │ │
│  │ StreamRenderer:帧批次 → 增量渲染(uPlot append)      │ │
│  │ WS 客户端(帧流) + REST 客户端                        │ │
│  └──────────────────────────────┬──────────────────────┘ │
└─────────────────────────────────┼─────────────────────────┘
                    REST(配置/统计/导出)   WS(控制 + 帧流)
┌─────────────────────────────────▼─────────────────────────┐
│ 后端(FastAPI 单进程)                                       │
│  ┌────────────┐ ┌────────────┐ ┌────────────────────────┐ │
│  │ REST API   │ │ WS 网关    │ │ 回放引擎 PlaybackEngine│ │
│  │ 文件/DBC   │ │ /ws/replay │ │ 速率控制/播放状态/批量 │ │
│  │ 解码/统计  │ │ /ws/live   │ │ 推送/订阅过滤/seek     │ │
│  │ /导出/配置 │ │ (广播帧流) │ └───────────┬────────────┘ │
│  └────────────┘ └────────────┘             │ FrameSource   │
│  ┌─────────────────────────────────────────▼────────────┐ │
│  │ 服务层:FileService / DbcService / DecodeService      │ │
│  │        StatsService / ExportService                  │ │
│  └─────────────────────────────────────────────────────┘ │
└─────────────────────────────────┬─────────────────────────┘
                                  │ FrameSource 统一接口
┌─────────────────────────────────▼─────────────────────────┐
│ 数据源层(可插拔)                                          │
│  ┌──────────────────┐  ┌──────────────────────────────┐   │
│  │ BlfReplaySource  │  │ CanLiveSource(后期)          │   │
│  │ 离线 BLF 回放    │  │ socketcan 实时接收            │   │
│  │ (帧索引缓存加速) │  │ (同 FrameSource 接口)        │   │
│  └──────────────────┘  └──────────────────────────────┘   │
│  帧索引缓存(内存 LRU + 磁盘索引可选)                        │
└──────────────────────────────────────────────────────────┘
```

**核心思想**:
1. **数据源可插拔**:`FrameSource` 统一接口,离线回放和实时接收都是它的实现 → 后端引擎与前端渲染完全不知道数据来自文件还是总线
2. **一条渲染管线**:前端 `StreamRenderer` 只消费"帧批次",播放模式和实时模式零区别。渲染策略:播放时 **x 轴固定全量范围(时间轴不动,曲线在固定时间轴上往后画)**,前端以 **rAF 毫秒级循环**取累积数据增量 setData(非粗粒度节流),保证曲线平滑无跳跃。同窗多信号渲染:各信号时间戳浮点不重合时,采用 **时间桶对齐**(自适应桶 = 信号中位周期一半,上限 5ms;时间戳量化到桶网格)——同窗信号同桶,x 并集不翻倍,per 数组 100% 非 null、零填充,连续线且**采样率零增加**;读数/tooltip 用 posToIdx;值表信号用采样点 mask 标记。uPlot 1.6 不支持嵌套 [t,v] 格式(实测全空白),必须列格式+桶对齐;官方确认:共享 x 列格式是有意设计(性能换对齐),非 bug;scatter/独立 x 支持(issue #107)多年 on hold;官方钦定做法 uPlot.join()(对齐+null 填充),本方案桶量化不膨胀数据,优于 join
3. **控制与数据分离**:REST 管配置/统计/导出(同步),WebSocket 管帧流(异步推送)

## 3. 技术选型(后台选型为重点)

### 3.1 后端框架/语言

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **Python + FastAPI** | async 原生 WebSocket;类型校验+Swagger;python-can/cantools 生态唯一选择 | 纯 Python 解析大文件慢(缓存/索引/C 扩展缓解) | ✅ **首选** |
| Python + aiohttp | WebSocket 好 | 无类型校验,生态弱于 FastAPI | 备选 |
| Node.js + Express/WS | 实时推送生态好 | CAN/DBC 解析库基本要自研 | ❌ |
| Go + gorilla/ws | 性能好,单二进制 | DBC/BLF 生态空白,开发成本高 | ❌ |

**结论:Python 3.11+ / FastAPI / Uvicorn(单 worker)**。理由:
- 生态决定论:python-can(BLF)+ cantools(DBC)没有替代
- FastAPI 原生支持 WebSocket 双向通信(播放控制 + 帧流推送),异步模型适合流式回放
- 性能短板通过"帧索引缓存 + 批量解码 + 可选 Cython 热点"解决,见 §7

**✅ 已定案(2026-08-23 用户拍板):Chart.js 4.5.1** —— 三库播放/阶梯线均实测可行,Chart.js 性能/体积全面领先(30万点 init 33.5ms、缩放 13.1ms、208KB);缩放/锚点用自绘 plugin(overlay afterDraw),不引第三方插件。切换完成 v99,备份 tag backup-lwc-v98 / backup-uplot-v93。

**Chart.js 渲染层要点(v99-v109 实测踩坑固化):**
- 销毁方法 **destroy()**(非 remove());tooltip 回调引用函数必须先验证存在(fmtNum 教训:图表每次 update 触发 tooltip 回调,未定义函数 → 渲染中断 → 播放失效)
- scales.x.top/bottom 是轴位置非绘图区 → overlay 竖线用 chart.chartArea
- 播放固定时间轴:scales.x.min/max 声明式(数据部分时保持,实测 [0,46.1])
- 值表信号:cantools NamedSignalValue 必须转数值(to_plain,静态/播放共用)—— 播放路径手动 json.dumps 会直接崩
- 缩放:x 范围钳制 [0,dur];普通滚轮不拦截(页面滚动),Ctrl+滚轮缩放
- 事件循环:前端渲染阻塞 → WS 不读 → TCP 缓冲满 → 后端 pump send 挂起 → 播放停(诊断条定位)

### 3.3 传输协议

| 场景 | 协议 | 理由 |
|---|---|---|
| 配置/统计/导出/文件 | REST(JSON) | 同步、幂等 |
| **帧流推送** | **WebSocket** | 需要双向:前端发 play/pause/seek 控制 + 后端持续推帧批次 |
| 心跳/断线重连 | WS ping/pong + 自动重连 | 回放中断可续 |

**帧批次协议**(前后端一致接口):
```jsonc
{
  "type": "batch",
  "seq": 42,                    // 批次序号(检测丢包)
  "t0": 1718000000.000,         // 回放起点(绝对秒,用于时钟对齐)
  "rate": 1.0,                  // 当前回放速率
  "frames": [
    { "ts": 1.234, "id": "0x21", "data": "AA BB CC", "channel": 0, "is_fd": true }
  ],
  "signals": {                  // 已订阅信号的解码值(增量)
    "ACU_3_CRC1": 190,
    "ACU_3_Resd1": 0
  }
}
```
前端只消费 `frames`/`signals` 追加到 uPlot,`seq` 用于断点续推;实时模式(后期)推送同样的 `batch`,前端零改动。

### 3.4 缓存与存储

| 层 | 方案 | 理由 |
|---|---|---|
| 帧索引 | 内存 LRU(4 文件/200 万帧)+ 磁盘索引可选(mmap) | 回放逐帧读取要随机定位,索引是回放性能地基 |
| 解码缓存 | 信号级 LRU(带 mtime/size 校验) | 统计/静态分析复用 |
| 配置 | JSON 文件(`data/config.json`) | 简单;无 DB 必要 |
| 元数据/分析结果 | 内存 + 可选 SQLite(文件列表/分析快照) | 1-5 用户,DB 非必需,先不引入 |

### 3.5 部署

- systemd + Uvicorn 单进程(回放引擎/数据源在进程内,状态简单)
- 静态文件由 Uvicorn 托管;版本号 `?v=N` 击穿 Edge 缓存
- 后期实时接收:同一进程内 `CanLiveSource` 线程/异步读 socketcan

## 4. 核心抽象:FrameSource

```python
# 统一帧源接口(离线/实时)
class FrameSource(ABC):
    def open(self) -> None: ...            # 打开数据源
    def next_batch(self, n: int) -> list[Frame]:   # 取下一批帧
    def seek(self, t: float) -> None: ...  # 定位到时间点(回放进度条)
    @property
    def time_range(self) -> tuple[float, float]: ...  # 数据时间范围
    def close(self) -> None: ...
    @property
    def is_live(self) -> bool: ...         # 实时源(无 seek,时间跟随)
```

- `BlfReplaySource`:帧索引缓存加速的离线回放;`seek` 用索引二分定位
- `CanLiveSource`(后期):socketcan 读取,`is_live=True`,无 seek

**回放引擎只依赖接口**:速率控制(时间缩放)、订阅过滤(只解码已选信号)、批量推送都建立在 `next_batch` 之上;实时源接入时引擎/前端零改动。

### 5.2 回放会话(WS)

- 每个 WS 连接 = 一个回放会话:`{source, engine, subscriptions}`
- 控制消息:`{"cmd":"play","rate":1.0}` / `{"cmd":"pause"}` / `{"cmd":"stop"}` / `{"cmd":"seek","t":12.3}` / `{"cmd":"subscribe","signals":[...]}`
- 帧批次按回放速率定时推送(如 50ms 一批,批内帧数 = 速率×时间窗);订阅信号实时解码进 `signals` 字段
- 断线重连:`seq` 续推(客户端告知最后收到的 seq,从该处续)

### 5.3 分析服务(静态,同步)

- signal-stats(min/max/mean/std/超范围/值表分布)
- cycle-stats(期望/实测周期/峰峰抖动/丢帧/峰值时间)
- bus-load(CAN/CAN FD 位时近似)
- 全部走帧索引缓存,0.02s 级响应

## 7. 性能设计

| 场景 | 方案 |
|---|---|
| GB 级 BLF 回放 | 帧索引缓存(首次全扫建索引,后续随机定位 O(log n));批读取 |
| 解码瓶颈 | 批量解码(一帧多信号一次解);热点函数可选 Cython/pyximport |
| 渲染 | uPlot min/max 保形降采样;增量 append 而非全量 setData |
| 回放速率 | 引擎按速率调度批推送,不丢帧(速率低则合并,高则抽样上限) |
| 内存 | 索引 + 解码缓存 LRU 上限;流式批处理不驻留全量帧 |

## 10. 与旧架构的差异(设计取舍)
